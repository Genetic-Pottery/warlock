# warlock-tui

The terminal front end of warlock. This crate ships the `warlock` executable — a `[[bin]]` target named `warlock`, distinct from the crate name `warlock-tui`, so `cargo run` from the repo root builds and runs `warlock` — and also exposes a library, `warlock_tui`, carrying the pure parts of the front end as ordinary reachable API shared by the binary and its own tests.

## What lives here

Only two files sit directly in this directory: `Cargo.toml`, which states the crate's dependency contract, and `README.md`, which is the closest thing this front end has to a spec — every key binding, every screen element, the manifest format, and the state-colour rules are written out there in full. All the actual code — `App`, rendering, input translation, the pact worker, the process-spawning agent, the event loop, the two modal gates — lives one level down in `src/`, whose own `WARLOCK.md` describes it in full; do not restate it here, read it before touching anything under `src/`.

## What this crate is for

It draws the current state of the work tree the engine loads from wherever the binary was launched, and turns keystrokes into requests back to the engine. It computes nothing about the tree itself: colour, freshness, and module boundaries are all decided by `warlock-engine` before a frame is drawn, and this crate only asks (`load_tree`) and renders what comes back. `p` is the only key that launches a pact run — a worker-thread call into the engine, and the only way a directory's state moves from gray to yellow to green on disk. `r` runs the same worker over a narrower list — only the stale directories of a pacted subtree — reporting through the same account, cancel handle, and single save. `s` writes a scope directly into the manifest synchronously, with no worker and no reload, because it is one string on one entry rather than a model pass.

## How the parts fit together

`Cargo.toml` declares the one hard rule this whole crate is built around: the dependency edge runs **TUI → `warlock-engine`, and never back**. This crate knows terminal and keystroke vocabulary; the engine knows nothing of either, and it never depends on this crate. Crossterm is deliberately not a direct dependency — code here uses `ratatui::crossterm`, Ratatui's own re-export of the backend it was built against, so the frontend and backend can never skew apart. `tempfile` is a dev-dependency only, used by the `warlock config` tests to write a real config file into a throwaway home directory rather than the developer's real one — the promise the engine's explicit home parameter exists to make keepable.

## What a reader has to know before changing anything

- **Domain logic belongs in the engine, never here.** What a pact means, how freshness is judged, prompt composition, and what makes a scope or sigil valid are all engine questions. If a change here starts deciding one of those things, it has crossed the boundary this crate exists to keep.
- **`p` pacts a whole subtree in one run, children before parents**, and the tree stays usable while it runs — the loop keeps drawing, moving, collapsing, filtering. No second `p`/`r` run starts while one is in flight; `Esc` cancels the run in progress (killing the `claude` child) rather than quitting, and only quits when nothing is running. On an already-pacted subtree, `p` un-pacts it instead — a manifest edit only, leaving the documents themselves on disk.
- **View state is never persisted.** Collapse set, filters, selection, scroll offset, and the two modal gates (quit confirmation, scope prompt) are held only in memory on `App` and nowhere else. This is structural, not a policy choice: the engine's serializable types (`Node`, `Tree`, the manifest schema) have no field any of it could ride out through. Every run starts fully expanded, unfiltered, files hidden, first row selected.
- **The manifest is `.warlock/pacts.toml`, one per repository, committed to git**, saved once per run via the engine's atomic `Manifest::save` — never once per directory — so a reader never observes a manifest mid-run. Documents are written the same atomic way, so a cancelled run leaves no half-written `WARLOCK.md`.
- **The purity boundary is the whole design of `src/`.** Only `claude.rs` spawns a process; only a handful of other files touch a real terminal, clock, or OS handle. Everything else is a pure function of its arguments, with the current instant always threaded in rather than read internally — what makes minutes-long pacts and multi-second debounce windows testable without a real terminal or a real clock.
- **This is not an IDE.** No prompt box, no chat transcript, no arbitrary file contents shown beyond a narrow document-viewer card, no free-text input beyond the two purpose-built fields for scope and sigil text. The panel is a freshness ledger — facts about what a pass did — and any addition should be checked against that register before it's built.
