The file implements the pure input-translation layer for a terminal UI (Warlock's TUI panel/tree view): translating keyboard and mouse events into intent types with no terminal I/O involved, so behavior is fully testable in isolation. It opens with a module doc comment explaining this purpose and naming its three key functions: `action_for` (keys to actions), `mouse_action` (mouse events to actions), and `press_for` (the "gate" that decides whether a keystroke goes to a confirmation dialog, a scope-editing prompt, or through to `action_for`).

Core types and functions:

- `Action` — the intents a keystroke can express: `Quit`, `CancelPact`, `ToggleFocus`, selection-movement variants (`SelectPrevious/Next/PageUp/PageDown/First/Last`), `ToggleCollapsed`, `TogglePactedOnly`, `ToggleFiles`, `TogglePact`, `Refresh`, `OpenScope`, `ToggleMouseCapture`, each documented with its rationale and interaction with a pact run in flight.
- `action_for(key, in_flight) -> Option<Action>` — pure mapping from a `KeyEvent` (presses only) to an `Action`. Esc quits normally but cancels an in-flight pact instead; Ctrl-C always quits. Maps Tab, arrow/vi keys, PageUp/Down, g/G, space, o, f, p, r, s, m to their actions.
- `is_ctrl_c(key)` — shared helper for the Ctrl-C test.
- `Pressed` — outcome of `press_for`: `Leave`, `Confirm(QuitConfirm)`, `Scope(Edited)`, `Act(Action)`, `Nothing` — mutually exclusive, and `Act` never carries `Action::Quit`.
- `press_for(key, confirm, prompt, in_flight) -> Pressed` — gating function: Ctrl-C always leaves first; then, if the quit-confirmation is open, keys go only to `answer_for`; then if the scope prompt is open, keys go only to `edit_for`; otherwise `action_for` is consulted, with `Action::Quit` reinterpreted as opening the confirmation (if idle) or leaving directly (if a pact is in flight).
- `WHEEL_NOTCH` constant (3) — rows/lines moved per wheel notch.
- `MouseAction` — mouse intents: `SelectNextBy`/`SelectPreviousBy`, `ScrollPanelDown`/`ScrollPanelUp`, `SelectRow`, `ToggleCollapsed`, `Focus(Focus)`.
- `mouse_action(mouse, size, app, confirm, prompt) -> Option<MouseAction>` — pure translation of a `MouseEvent`; returns `None` if either window is open. Only scroll and left-button-down are handled; other events are dropped, since continuous pointer movement without action avoids per-move redraw costs.
- `wheel(hit, tree, panel)` and `click(hit, app)` — helpers routing wheel notches and clicks by which region (`Hit` variant) was hit, including "second click on the selected row toggles collapse."

A `#[cfg(test)] mod tests` follows, defining a `press()` helper and tests for `action_for` covering: q/Esc quitting when idle, Esc cancelling mid-pact while q/Ctrl-C still quit, Esc being the only key whose meaning changes mid-pact, Ctrl-C detection (with/without shift/caps lock), and individual tests for Tab, arrow/vi movement, page keys, g/G, space, o, f, p, r, s, and m — each checking the binding works, releases/repeats are ignored, and neighboring keys don't misfire.

Two nested test submodules follow:

- `mod gate` — tests for `press_for`'s gating behavior, with fixtures `SIZE`, `DIRECTORY`, `INERT` (tree-bound keys), a `Round` enum (`Stayed`/`Left`) standing in for event-loop control flow, `app_on_screen()`/`app_in_use()` builders, and `round`/`round_under` reimplementing the loop's dispatch arms. Tests verify: the "off defaults" fixture assertion; Esc/q opening a confirmation instead of quitting; the confirmation swallowing all tree keys; Yes/No answers behaving correctly; double-Esc not accidentally quitting; Ctrl-C leaving immediately regardless of dialog state; in-flight pacts suppressing the confirmation; and the scope prompt similarly swallowing keys with special handling for Ctrl-C/Esc/q.

- `mod pointer` — tests for `mouse_action`, with fixtures `SIZE`, column/row constants (`IN_TREE`, `IN_PANEL`, `FIRST_TREE_ROW`, `FIRST_PANEL_LINE`, `TREE_HEADER`, `FOOTER`), helper constructors (`wheel_down`, `wheel_up`, `left_click`, `event`), an `app_on_screen()` fixture (25 rows, more than fit on screen), an `asks()` helper wrapping `mouse_action` with closed windows, and `round`/`round_under` reimplementing the loop's mouse-dispatch arms. Tests cover: screen geometry constants; wheel notches moving selection by 3 with clamping at the ends; wheel scrolling the panel; wheel following the pointer's pane regardless of focus; notches over footer/borders doing nothing; clicks selecting rows and taking focus; clicks mapping window-relative offsets to absolute row indices when scrolled; double-clicks toggling collapse on directory rows but not file rows; and clicks in the panel only taking focus.

Further tests in `mod pointer` include: a click on the tree header while focus is on the panel producing `MouseAction::Focus(Focus::Tree)`, moving focus to the tree without changing the current selection; a click below the last row (with a single-row `App` built via `App::from_rows`/`Row::new`, a `WARLOCK.md` file, and `NodeState::PactedStale`) still focusing the tree but leaving the row list and selection unchanged; clicks on the footer or a border (iterating a list of tree/panel coordinates) always yielding `None`; and a broad test that all mouse event kinds other than wheel and left-press (Moved, Drag, Up, Down for right/middle buttons, ScrollLeft/Right), across various coordinates, are read and dropped.

The suite closes with two tests confirming that mouse input is fully ignored while a modal is up: one sets up specific app state (files toggled, a selected row, panel scroll, panel focus), clones it as `before`, opens a `QuitConfirm`, feeds a battery of wheel and click events through `mouse_action`/`round`, and asserts every result is `None` and the app state is unchanged; the other does the same while a `ScopePrompt` (with both empty and filled text) is open, using `round_under` to drive events through a specific prompt state, again asserting no mouse input leaks through and the app is unchanged.

The file ends with the closing braces of the test module and its enclosing module.
