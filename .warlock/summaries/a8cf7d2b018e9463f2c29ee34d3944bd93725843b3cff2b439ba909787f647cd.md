This file implements a transport layer that runs the `claude` CLI as a child process, providing the sole location in the codebase where a child process is spawned, sitting behind an `Agent` trait defined elsewhere.

It opens with an extensive module-level doc comment laying out the concurrency design: the engine builds requests and defines response/error types but never spawns processes itself; this module owns that responsibility. The comment walks through several hazards and their fixes — pipe-filling deadlocks solved by reading stdout/stderr on separate threads while waiting; stdin-EOF handling via a dedicated writer thread that drops its handle; and the fact that `Child::wait` takes `&mut self` (making cross-thread killing impossible) solved by a polling waiter thread over a shared `Mutex<Child>` reporting via an `mpsc` channel. It introduces two cooperating handle types: `Cancel` (lets a caller stop an in-flight pass by killing the child) and `Activities` (lets a caller receive live progress events without seeing tool results, prose, or thoughts). It explains the use of `--output-format stream-json` and `--include-partial-messages` to surface live signals like "thinking" and "writing" without exposing content.

Imports bring in the engine's `Agent`, `AgentError`, `AgentRequest`, and `AgentResponse` types.

A block of well-documented constants and helpers follows: `INVOCATION_TIMEOUT` (5 minutes, with rationale); `PROGRAM` (`"claude"`); `ARGS`, the fixed CLI arguments (`--print`, `--output-format stream-json`, `--verbose`, `--include-partial-messages`), each justified; `MODEL` (`"claude-sonnet-5"`, pinned explicitly rather than inherited from user config); `EFFORT` (`"low"`, with cost/quality reasoning); `SYSTEM_PROMPT`, a short fixed prompt replacing the CLI's default ~9k-token coding-agent prompt (cost drops from $0.024 to $0.0016 per invocation); `NO_TOOLS` (empty, since passes need no tools); `MODEL_VAR`/`EFFORT_VAR` environment variable names (`WARLOCK_MODEL`, `WARLOCK_EFFORT`) as the sole user-facing configuration escape hatch; `or_default` and `overridden`, pure functions implementing "empty counts as unset" override logic; `CONTENT_GUARD`, a string separating instructions from directory content to guard against file content that looks like instructions; `render(request: &AgentRequest) -> String`, which serializes a request's prompt, files, and child documents into one string for stdin — handling three file states (sent whole, summarized, or omitted), treating non-UTF-8 bytes as "not text," appending a directory-name heading, and returning the prompt unchanged when there are no files/children (for map/reduce passes); `default_args()`, which builds the full per-instance argument vector incorporating env overrides; and `POLL_INTERVAL` (10ms), the waiter thread's polling granularity.

Two documented "port" types follow, each with doctests. `Cancel` is a clonable `Arc`-backed handle wrapping an `AtomicBool` flag and a `Mutex<Option<Arc<Mutex<Child>>>>`, with methods `new`, `cancel` (latches the flag and kills/reaps any running child, race-safe against registration), `is_cancelled`, `register` (offers a child to be tracked, refusing if already cancelled), and `finished` (clears the tracked child). An `Activity` enum has variants `Tool { name, detail }`, `Thinking`, `Writing`, and `Cost { usd }`, deliberately excluding tool results, prose, or thought content. `Activities` is a clonable `Arc<dyn Fn(Activity)>` sink with `new`, a no-op `none`/`Default`, `report`, and a `Debug` impl that just names the type.

`ClaudeAgent` is the main struct implementing `Agent`, holding `program`, `args`, `timeout`, `cancel`, and `activities` fields, configurable via builder methods (`with_program`, `with_args`, `with_timeout`, `with_cancel`, `with_activities`) and accessors, plus `spawn` (starts the child with piped stdio in the request's directory) and `spawn_error` (disambiguates "program not found" from "directory not found," since the OS error is otherwise ambiguous). `Default` delegates to `new`.

The `Agent::run` implementation orchestrates a pass: it checks cancellation before spawning; spawns the child; takes its stdin/stdout/stderr; spawns a writer thread for stdin (the rendered prompt) and reader threads for stdout/stderr (`read`/`drain`); wraps the child in `Arc<Mutex<Child>>`; registers it with `Cancel` (killing immediately if already cancelled); and spawns a waiter thread/channel pair (`watch`). It then does `recv_timeout` and handles: successful exit while cancelled (treated as cancellation, output discarded), successful exit (joins threads, collects output, calls `judge`), a waiter I/O error, a timeout (kills the child and returns `AgentError::TimedOut`), or an unreachable disconnected channel. Finally it calls `cancel.finished()` and rewrites any error to a cancellation error if cancellation occurred. Supporting helpers: `cancelled()` builds an `AgentError::Io` with `ErrorKind::Interrupted`; `judge(status, document, stderr)` turns exit status and captured output into a result, preferring failure over emptiness and treating whitespace-only output as empty.

A pure, no-I/O submodule (`stream`) parses individual JSON lines of the `stream-json` output format into a `Reading { activities, text }` struct. It defines `DETAILS`, a lookup table of six tools (Read, Edit, Write, Glob, Grep, Bash) each mapped to the one input key worth reporting, and functions `read_line` (dispatches on the `"type"` field: `assistant`, `result`, `system`/`thinking_tokens`, `stream_event`, or a default), `read_activities` (extracts tool_use/thinking blocks from an assistant message, ignoring text and tool_result blocks), `read_block_start` (detects a text `content_block_start` inside `stream_event` lines, signaling `Writing`; ignores `thinking` block starts since those are already covered by `thinking_tokens` system lines), `read_block` (per-block dispatch), `read_detail` (looks up the whitelisted argument for a tool), and `read_result` (extracts `total_cost_usd` and the result text from the final result line). Everything here fails soft — unrecognized shapes produce empty `Reading` defaults rather than errors, since a documentation decoration isn't worth failing a pass over.

Back in the outer module: `read` (spawns a thread reading stdout line-by-line, calling `stream::read_line` on each, reporting activities live via `Activities` and accumulating the final document using lossy UTF-8 conversion), `drain` (spawns a thread reading a source to completion into a `Vec<u8>`, used for stderr, inspected only after exit), `collect` (joins a reader thread's handle, converting a panic into an `AgentError::Io`), `watch` (spawns the waiter thread polling `try_wait` on the shared `Mutex<Child>` at `POLL_INTERVAL`, reporting exit status over the channel), `kill_and_reap` (kills and waits on a child, swallowing errors), and `lock` (recovers from mutex poisoning via `PoisonError::into_inner` rather than panicking again, since a poisoned lock around a child still needs to be killed/reaped).

The remainder is a `#[cfg(test)] mod tests` containing extensive unit tests not requiring a real `claude` binary: default agent configuration and arguments; `render` behavior across file states (present/omitted/summarised), non-text/binary handling, child-document rendering, directory-name heading, and prompt-only rendering for map/reduce requests; the `or_default`/override logic; the empty `--tools` argument; replacing args via `with_args`; a `NotFound` error test with a nonexistent program name; `Cancel` behavior across threads; `Activities` swallowing reports when unattached and delivering them across threads when attached; and detailed tests of `stream::read_line` covering tool whitelisting/detail extraction, missing-argument tool calls, thinking-block bare-fact behavior, exclusion of tool_result/prose content, malformed/irrelevant JSON lines, `thinking_tokens` system lines, `stream_event` text-block-start (Writing) detection, other `stream_event`/`system` shapes being ignored, final result-line parsing (document plus cost), partial result lines (missing cost or missing text), and multi-block assistant lines producing ordered activity sequences.

Test helpers follow for a `#[cfg(unix)]` submodule: constants `AT_MOST` and `PASS` (canned JSON stream lines simulating a realistic pass) and `DOCUMENT`; `reported()` giving expected activities; `stand_in` for building a shell-script-based fake `claude`; `printing` for building a printf-based script; `listening`/`drained` for capturing reported activities; `is_cancelled` as a predicate; and `pid`/`scratch`/`clean_up` for temp-directory-based process tests.

Unix-only integration tests then follow, covering: a clean run via `cat` echoing stdin as a fake single-line stream; a full canned pass verifying reported activities and the returned document; a test verifying activities arrive incrementally while the pass is still running (confirmed by a reported timestamp arriving well before completion), rather than all at once at the end.

Further integration tests cover robustness and edge cases. `garbage_in_the_stream_costs_neither_the_document_nor_an_activity` feeds malformed/foreign lines (a stderr-style warning, invalid JSON, an unrecognized event type, blank lines) interleaved with canned stream lines, confirming the document and reported activities are unaffected. `nothing_from_a_tool_result_reaches_the_port_however_big_it_is` injects a ~0.25MB payload as a `tool_result` in both a `user`-role message and a misfiled `assistant`-role message, confirming none of that payload reaches reported activities. `a_thought_reaches_the_port_as_the_bare_fact_that_there_was_one` streams a `thinking` block with secret text and a signature, asserting only `Activity::Thinking` and `Activity::Cost` are reported and neither the secret text nor signature appear anywhere in the output. `what_the_pass_cost_comes_back_from_its_result_line` shows the cost is taken verbatim from the CLI's result line (`total_cost_usd: 1.25`) rather than recomputed. `a_pass_nobody_listens_to_runs_exactly_as_it_did_before` runs several scripts (success, exit-3 error, immediate exit 0, an incomplete stream, and a run in a nonexistent directory) both with and without a listening port attached, comparing results to confirm attaching a listener changes nothing, while also confirming activities are still reported when a listener is attached (proving it isn't silently disconnected). `the_pass_runs_in_the_directory_the_request_names` writes a marker file into a scratch directory and runs `ls` via a stand-in agent, confirming the marker appears in output, proving the child's working directory follows the request. `a_non_zero_exit_carries_its_status_and_its_stderr` expects `AgentError::Failed { code: Some(3), stderr }` with stderr trimmed to "boom" from a script that exits 3 after printing to stderr. `a_clean_run_that_says_nothing_is_empty_output` shows four scripts (no output, blank lines only, an incomplete stream lacking a result line, and a result line whose document is whitespace) all yield `AgentError::EmptyOutput`. `a_missing_directory_is_io_rather_than_a_missing_binary` confirms running in a nonexistent directory yields `AgentError::Io`, distinguishing it from a missing binary despite an identical underlying `NotFound` syscall error. `a_big_prompt_and_a_chatty_child_do_not_deadlock` sends a 200,000-byte prompt against a chatty child producing ~20,000 lines of thinking output, confirming no deadlock and that all activities and the document arrive intact.

Timeout and cancellation tests follow: `a_hanging_pass_times_out_and_its_child_stops` (with a Linux-only companion `a_timed_out_child_is_reaped_not_left_a_zombie`) runs a forever-looping script under a short timeout, confirming `AgentError::TimedOut { after }` returns promptly, the child stops writing after timeout, and on Linux that `/proc/<pid>` is gone (not a zombie). `a_cancel_from_another_thread_ends_the_pass_promptly` spawns a thread that waits for the child's pid file then calls `cancel.cancel()`, confirming the run ends quickly with a cancellation error despite a 30s sleep in the script and an effectively unbounded timeout. `a_cancel_does_not_wait_on_output_a_survivor_still_holds` uses a script that forks a background "survivor" process distinct from the main child (mimicking a tool subprocess inheriting the child's pipes), verifying cancellation doesn't block on that survivor's pipe remaining open, and manually killing the leftover survivor in cleanup since the harness's kill only reaches the actual child. `a_cancelled_childs_process_is_gone_afterwards` (Linux-only) checks `/proc/<pid>` is gone after cancellation, confirming reaping as well as killing. `a_pass_started_after_a_cancel_spawns_nothing_at_all` cancels before running and asserts no child process is spawned at all. `a_handle_nobody_cancels_leaves_the_run_exactly_as_it_was` runs a clean full pass with a `Cancel` handle attached but never triggered, confirming correct output and that calling `cancel.cancel()` afterward is a no-op.

Finally, after the test submodule's closing brace, a last top-level test, `a_failure_arrives_quickly_rather_than_after_the_timeout`, builds a `ClaudeAgent` pointed at a nonexistent program with the full invocation timeout set, and asserts the resulting failure returns in under 5 seconds — confirming that failure to invoke the binary is detected immediately rather than by waiting out the timeout.
