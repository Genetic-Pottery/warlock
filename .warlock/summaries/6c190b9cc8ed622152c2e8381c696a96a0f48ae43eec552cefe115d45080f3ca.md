This file implements a "pact" workflow — running documentation generation over a directory tree via an external agent (a `claude`-like CLI tool), plus its twin operation "refresh," both built on shared worker/channel/account machinery, and the TUI application state that displays run progress. It also implements cancellation, watcher-driven reloads, and an extensive test suite covering all of this.

It opens with a module doc-comment explaining the overall purpose: a pact is a keystroke that triggers a worker-thread operation writing documentation and a manifest to disk; refresh is its twin, re-running over stale subtrees. Both are driven by shared worker/channel/account machinery, with cancellation handled via a `CancelGuard` that distinguishes Esc-cancel (which still saves partial work) from quitting (which kills the child process and discards nothing extra). Core imports follow: std concurrency/filesystem primitives, and types from `warlock_engine` and `warlock_tui` for agents, manifests, trees, node states, pacting operations, and app/UI types.

Key items defined:

- Constants `PACT_LOST` and `PACT_CANCELLED`: footer messages for a worker that panicked without reporting, and for a run the user cancelled with Esc; also `DOCUMENT_FILE` ("WARLOCK.md"), the filename the engine writes per pacted directory.
- `Running`: holds the event receiver, a `CancelGuard`, the `Work` describing what was requested, and a pre-run `App` snapshot for restoring state on failure.
- `Work`: `Pact(PactToggle)` or `Refresh(PathBuf)`, with methods for the subtree root, UI-facing kind, and whether it's cancellable (un-pact, being synchronous manifest editing, is not).
- `CancelGuard`: wraps a `Cancel` handle, always cancels on `Drop` so no orphaned `claude` subprocess survives any exit path.
- `PactEvent`: worker-to-UI channel messages — `Starting`, `Doing(Activity)`, `Summarising`, `Documented`, and `Finished(Result<Toggled, String>)` (sent exactly once, ending the channel).
- `activity_port` and `Reporting` (implementing `PactObserver`): bridge engine progress callbacks into `PactEvent` sends, checking the cancel handle to decide whether to continue or stop.
- `spawn_pact`/`start_run`: spawn the worker thread with its own `ClaudeAgent` clone, cancel handle, and activity port, returning a `Receiver<PactEvent>` (or a full `Running`).
- `run_pact`: the worker thread body — calls `apply_toggle`, rewrites the outcome via `cancelled` if the run was cancellable and got cancelled, sends one `Finished` event.
- `pact_press`/`refresh_press`: handle keypresses — refuse silently (a UI flag, not a message) if a run is in flight; otherwise delegate to `app.toggle_pact()`/`app.refresh()` and start an account for genuine pacts/refreshes.
- `apply_progress`: the per-frame function draining the worker's channel, updating panel/footer state for each event variant, painting directories green on `Documented`, treating a disconnected channel as an implicit `PACT_LOST` finish; afterward clears in-flight state, dispatches success (updates manifest, paints subtree, sets message) or failure/loss (`restore()` from the pre-run snapshot), calls `close_account`, and calls `reload_tree`, returning the new `Tree` if successful.
- `close_account`/`section_outcome`: finalize the panel's account sections, marking cancellation specially and deriving outcomes from failures or from stat'ing `WARLOCK.md` on disk (`Outcome::Wrote` with byte size, or `Outcome::Refused`).
- `restore`: reverts `app` to a prior snapshot but preserves the current account as a historical record, then sets a message.
- `section_label`: names a directory relative to the tree root, falling back to the absolute path if needed.
- `Toggled`: outcome payload — resulting `Manifest`, whether `granted`, optional one-line `message`, and a list of `Refusal`s.
- `Refusal` (with `From<&PactFailure>`): pairs a directory with a one-line failure reason.
- `apply_toggle`: performs the actual pact/refresh/un-pact engine call, saves the manifest exactly once, returns `Result<Toggled, String>` with errors flattened to one line.
- `described`: turns a `PactedSubtree` result into a `Toggled`, deciding `granted` from failures, collecting `Refusal`s, building the footer message via `pact_message`.
- `pact_message`: builds the one-line footer summary from failures/problems, quoting the first issue and appending a count of the rest ("(and N more)"), or `None` if nothing went wrong.

The remainder of the file (well over half its length) is a `#[cfg(test)]` module with extensive fixtures and unit/integration tests. Fixtures include: `ROOT`, a `Canned` fake `Agent` (returns canned documents, can simulate refusals, mid-run cancellation, records visited directories); `Scratch` (temporary scratch repository with cleanup on `Drop`); helpers `toggle`, `refreshing`, `pact_of`, `one_crate`/`one_crate_to_load`/`two_crates`/`eight_crates` (sample repositories), `load`, `at`, `panel_text`, `nowhere`, `state_of`, `documents`, `run_and_apply`, `events_of`/`events_from`, `fractions`, `announced`, `outcome_of`, `pacted`, `recorded`/`recorded_from`, `replay`/`replay_work` (frame-by-frame event replay with duplicate-message collapsing), `document_bytes`, and constants `FRAME`, `CRATES`, `MINIMUM_DOCUMENT_BYTES`, `NOT_REFRESHED`.

Tests cover: a pact documenting and granting every directory in a subtree; the manifest being written exactly once, at the end; entries outside the pacted subtree being preserved untouched; refused directories and multiple simultaneous problems being summarized on one footer line with a "(and N more)" count; un-pacting saving a manifest without the subtree while keeping documents on disk; directories outside the repo root being refused rather than stored; a manifest that fails to save leaving the previous one alone (Unix-only, via chmod); worker events naming each directory in turn and reporting how the run went; activity events landing between a directory's `Starting` and the next; large files being split into numbered chunked "summarising" passes announced in order without affecting outcome; a spawned run reporting real activity (tool use, cost) over its channel via a faked `claude` CLI shell script, ending in exactly one `Finished` event; a missing configured program producing a single-line failure naming the binary; keypress refusal behavior (in-flight refusal is silent via a flag, idempotent, but pressing on a file or ignored directory uses the app's message and opens no account); pact/un-pact/refresh account lifecycle (starting, preserving, and resetting the account); refresh skipping fresh directories while still ending fully fresh; cancellation during a two-crate pact (descent order, stopping between rather than mid-directory, partial manifest saves, color states, surviving documents, `granted: false` with `PACT_CANCELLED`); a cancelled refresh exercised through the real event loop with exact panel wording; a `Running` value's `Drop` cancelling its guard so no child process is orphaned; `apply_progress` filling the panel section-by-section with ticking clocks and accumulating costs, handling multiple directories, finalizing on `Finished` (with unreported directories marked "refused — no document was written"), turning subtrees green early on `Documented` without duplicating rows, leaving unrelated tree/reader state undisturbed, and treating a dead channel as `PACT_LOST` without altering the panel; full end-to-end panel text assertions including byte counts and costs, refusal reasons matching the footer, and cancellation wording with exact line counts; a refresh counting only the directories it actually visits rather than the whole pointed-at subtree (verified against an 8-crate fixture); a pass that never reports its cost leaving the total marked incomplete; a worker whose channel dies mid-run ending cleanly via `PACT_LOST` and restoring pre-run state; a finished pact causing new document rows to appear in green with no message; reload preserving reader position (selection, collapsed set, scroll, filters) despite tree structure changes; un-pact triggering the same reload rule; a failed reload keeping the on-screen tree and prefixing the footer message with `NOT_REFRESHED`; the pact's own message taking priority over the reload's when both have something to say; and a reload that succeeds but encounters problems (Unix-only, via chmod) still adopting the new tree while reporting a count of problems, checking that the "could not be hashed" message includes "and 1 more like it" and contains no newline (so it never wraps and hides a row).

The test module ends with a nested `mod watching`, documented as testing how the main loop reacts to filesystem changes: that a watcher-triggered reload happens, preserves reader state, and is deferred while a pact is in progress. No real filesystem watcher is used — `Watching::Off` stands in, and change events are simulated by telling the `WatchPolicy` directly that a path was "accepted," bypassing the OS-level watcher (tested elsewhere). It imports `Duration`/`Instant`, `manifest_path`, `QUIET_PERIOD`, `RELOAD_CEILING`, `WatchPolicy`, `Watching`, and reuses many parent-module items, plus `POLL_INTERVAL` and session helpers `NOT_WATCHING`, `Watched`, `note`. A helper `unwatched` builds a `Watched` value with watching disabled but a real `WatchPolicy`. Three tests follow: one confirming a watcher-driven reload (after `QUIET_PERIOD` elapses, not before) updates only the changed node's state while leaving selection, collapsed set, filters, scroll, header, and message untouched; one confirming that while a pact is in flight, no elapsed time (up to `ROUNDS = 12` iterations, exceeding both `QUIET_PERIOD` and `RELOAD_CEILING`) triggers a reload, and that the run's own end-of-run reload fires once, clears the deferred flag, and doesn't double-fire on a later round; and one confirming the "live updates are off" footer note (`NOT_WATCHING`-prefixed, no newline) is shown once via `note()`, yields precedence to a pact's own message once posted (and stays yielded even if `note()` is called again), and does not appear at all when a watcher starts successfully.
