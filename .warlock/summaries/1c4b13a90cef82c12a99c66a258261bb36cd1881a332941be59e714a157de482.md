This file implements the input-translation layer for a terminal UI application (the "warlock" TUI panel), turning raw keyboard and mouse events into pure, terminal-independent intent values so the event loop elsewhere can react to named consequences. It opens with a module-level doc comment explaining this purpose and previewing three key functions — `action_for` (keyboard, no window state), `press_for` (keyboard, aware of a quit-confirmation gate and a scope-editing prompt), and `mouse_action` (pointer) — along with the rationale for giving Ctrl-C and an in-progress-run ("in_flight") state special treatment.

The file's structure is:

1. An `Action` enum listing what a keystroke can ask the app to do (Quit, CancelPact, ToggleFocus, SelectPrevious/Next/PageUp/PageDown/First/Last, ToggleCollapsed, TogglePactedOnly, ToggleFiles, TogglePact, Refresh, OpenScope, ViewFile, EditFile, SwapCard, ToggleMouseCapture), each variant documented with its keybinding mnemonic, its interaction with in-flight runs, and a note that refusals (e.g. acting on a non-file row) are handled by the app/loop rather than here.

2. `action_for`: a pure function of a key event and an `in_flight` flag returning an optional `Action`. It only reacts to key presses (ignoring releases/repeats), and maps Ctrl-C, Esc (whose meaning depends on `in_flight`), `q`, Tab/BackTab, movement keys (arrows, hjkl-style, PageUp/Down, g/G), Space, and single lowercase letters (`o`, `f`, `p`, `r`, `s`, `v`, `e`, `m`) to actions, with comments justifying each binding choice.

3. A `Pressed` enum describing the outcome once the quit-confirmation gate has processed a key (Leave, Confirm, Scope, Act, Nothing), structured so that quitting can never bypass the confirmation gate.

4. An `is_ctrl_c` helper and `press_for`, the gating function itself: given a key plus quit-confirmation state, scope-prompt state, and `in_flight`, it applies precedence — Ctrl-C always leaves immediately; an open quit-confirmation dialog swallows the key; an open scope prompt swallows the key; otherwise `action_for` is consulted, with `Action::Quit` reinterpreted as opening the confirmation dialog (if not in_flight) or leaving directly (if in_flight).

5. Mouse handling: a `WHEEL_NOTCH` constant (3), a `MouseAction` enum (SelectNextBy/PreviousBy, ScrollPanelDown/Up, SelectRow, ToggleCollapsed, Focus), and `mouse_action`, which turns a mouse event, terminal size, app state, and the two dialog states into an optional `MouseAction`. It returns nothing while either dialog is open, otherwise locates the click target via `hit_test` and dispatches wheel events through a `wheel` helper (routed by pane regardless of current focus) and left-button-down events through a `click` helper (which also implements "clicking an already-selected row toggles its collapse state").

6. `wheel` and `click`: pure helper functions translating a located hit (and, for click, the app state) into an optional `MouseAction`.

7. A large `#[cfg(test)] mod tests` block, which makes up the remainder and majority of the file. It first tests `action_for` exhaustively: quit/cancel behavior with and without in-flight runs, Ctrl-C variants, focus toggling, movement keys, collapse toggling, filter toggles (`o`, `f`), pact toggle (`p`), refresh (`r`), scope (`s`), view (`v`), edit (`e`), swap card (BackTab), mouse-capture toggle (`m`), and checks that unbound keys, releases, and repeats do nothing.

8. A nested `mod gate` submodule testing `press_for`'s precedence logic against the quit-confirmation and scope-prompt states, using fixtures `app_on_screen`, `app_in_use`, `round`, and `round_under`.

9. A nested `mod pointer` submodule testing `mouse_action`, built around: a `rows()` fixture of 25 rows (one root directory with 24 children, each child a directory containing one file), sized to force scrolling and to exercise both refused and permitted collapse actions; `app_on_screen()`, which builds an app from those rows with viewport/panel heights fixed to a `SIZE` constant and file rows initially hidden; `asks()`, which calls `mouse_action` with both dialogs closed; and `round`/`round_under`, which simulate one event-loop iteration by computing a `MouseAction` and applying the same mutations (selection movement, panel scrolling, row selection with focus change, collapse toggling, focus change) that the real event loop would, so tests exercise identical logic paths.

   This submodule's tests cover: the fixed screen geometry constants used throughout; wheel scrolling over the tree (including its header) moving selection by three and clamping rather than wrapping at list ends; wheel scrolling over the panel moving it three lines; wheel input acting on whichever pane the pointer is over regardless of current focus, without changing focus itself; wheel events over the footer or a border doing nothing; left-clicks on a tree row selecting it and moving focus to the tree, with click coordinates translated using the scroll offset rather than raw screen position; a second click on an already-selected directory row toggling it open and closed, while a second click on a file row does nothing further (files can't collapse); clicks in the panel or on the tree header changing only focus; clicks below the last row or on the footer/a border doing nothing to selection or rows; mouse move, drag, right/middle-button, and horizontal-scroll events all being read and dropped regardless of position (a deliberate scope limitation to avoid redraw costs from tracked hover); and, while either the quit-confirmation dialog or the scope-entry prompt is open, all mouse actions (wheel and click variants, including with the scope prompt's text field both empty and filled) being swallowed with no change to app state, since those dialogs are keyboard-only.

The tests rely on supporting items — `App`, `Row`, `NodeState`, `Focus`, `QuitConfirm`, `ScopePrompt`, screen-geometry helpers/constants (`SIZE`, `viewport`, `panel_height`, `tree_height`, `IN_TREE`, `IN_PANEL`, `FIRST_TREE_ROW`, `FIRST_PANEL_LINE`, `TREE_HEADER`, `FOOTER`), and mouse-event constructors (`wheel_down`, `wheel_up`, `left_click`, `event`) — that are used but not defined within the test module itself.
