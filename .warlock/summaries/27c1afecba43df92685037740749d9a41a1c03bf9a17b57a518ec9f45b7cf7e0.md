These are the complete and only contents of `pacting.rs`, presented as a single part.

The file implements the machinery behind Warlock's two long-running keystrokes — the pact key (`p`) and the refresh key (`r`) — which are the only actions in the TUI that write to disk and take longer than a frame, and are therefore run on a background worker thread rather than the event loop's own thread.

**Module doc comment** frames the whole file: `Pact<P>` is what the event loop keeps between frames (the agent used to make runs, and the run currently in flight, if any). `Pact::press` decides what a keystroke means and starts a worker; `Pact::keep_up` drains the worker's channel each frame; `Pact::stop` and `Pact::running` are the two questions the rest of the loop asks. A pact and a refresh share nearly all of this machinery, differing only in which engine entry point is called and how the footer words it, unified under one `Work` enum. Stopping a run has two distinct paths: Esc cancels gracefully (letting the worker finish hashing/saving/reporting what it completed), while quitting drops a `CancelGuard` that kills the in-flight `claude` process outright.

**Constants**: `PACT_LOST` (worker died without reporting, i.e. panicked) and `PACT_CANCELLED` (the reader pressed Esc) — messages shown on the footer.

**Core types**:
- `Pact<P>` — holds the agent and `Option<Running>`.
- `Reloaded(Option<Tree>)` — signals a run ended this round and carries the tree from the resulting reload.
- `Running` — a run in progress: the event receiver, a `CancelGuard`, the `Work` being done, and a copy of the `App` from before the keystroke painted anything (used to restore on failure).
- `Work` enum — `Pact(PactToggle)` or `Refresh(PathBuf)`, with methods for the path, `Descent` kind, `Run` kind, and whether it's cancellable (un-pact is not, since it's synchronous manifest arithmetic).
- `CancelGuard` — wraps `Cancel`, cancels on `Drop` so no exit path can leave an orphaned `claude` process running.
- `PactEvent` — the six-variant enum sent over the worker's channel: `Starting`, `Doing`, `Summarising`, `Requesting`, `Documented`, `Finished`.
- `Reporting` — implements `pact::Observer`, translating engine callbacks into `PactEvent`s sent over the channel, checking cancellation between directories.

**Key functions**:
- `activity_port` — builds an `Activities` port that forwards to the event channel.
- `spawn_pact` — spawns the actual worker thread, owning its own clones of manifest, root, work, and agent.
- `start_run` — bundles everything into a `Running` value.
- `run_pact` — the worker thread's body: calls `apply_toggle`, rewords the outcome if cancelled, sends exactly one `Finished` event.
- `cancelled` — transforms a `Toggled` outcome to reflect a stopped run (ungranted, `PACT_CANCELLED` message) without discarding what was actually saved.
- `pact_press` / `refresh_press` — decide what a keystroke means: refuse if a run is already in flight (wording the footer's flag), refuse if crossing a closed scope boundary (`closed_scope`), and for pacting specifically, refuse an un-pact that would drop a scope boundary held below the row (`blocked_unpact`). These encode the scopes/sigils boundary system described in the project's CLAUDE.md — un-pacting is refused because it would irreversibly drop scoped entries.
- `blocked_unpact` — the downward-looking check: whether un-pacting a row would destroy a scope boundary on a descendant, distinct from `closed_scope`'s upward check.
- `pressed_p` — a test-only seam exposing `pact_press` to the shell crate's tests, so the TUI key and `warlock unpact` can be shown to agree.
- `drain` — the heart of `keep_up`: drains all buffered `PactEvent`s, updates the panel/account and tree-row colors live (sections open per directory, activities/summarising/requesting lines recorded, `Documented` events paint subtrees green and insert document rows immediately), then closes out the account, and performs exactly one tree reload at the very end regardless of outcome (success, partial failure, worker death, or cancel).
- `close_account` / `section_outcome` — end every open panel section with either its refusal reason or the document it wrote (stat'd from disk).
- `restore` — puts the view back to the pre-keystroke copy while preserving the run's account (a run's history is not undone even if its manifest changes are).
- `section_label` — spells a directory relative to the tree root, matching footer wording.
- `Toggled` — outcome of applying a toggle: resulting manifest, whether granted, a footer message, and a list of `Refusal`s (one per failed directory).
- `Refusal` — flattens an engine `pact::Failure` to a directory + one-line reason.
- `apply_toggle` — calls `descend` (shared with the shell's CLI commands) to do the actual walk/pact/refresh/unpact, then builds a `Toggled`.
- `described` — shared post-processing for pact and refresh outcomes (both produce `PactedSubtree`).
- `pact_message` — builds the one-line footer summary from failures and byte-cap problems, first one verbatim plus a count of the rest.
- `DOCUMENT_FILE` constant — `"WARLOCK.md"`.

**Extensive `#[cfg(test)] mod tests`** (the bulk of the file) covers: a `Canned` fake `Agent` that records every request and can simulate refusals/cancellation; a `Scratch` helper for building throwaway repositories; and dozens of tests exercising — granting a whole subtree; single-save-at-the-end semantics; entries outside the pact being untouched; refusal wording and counting; un-pacting; paths outside the repo root; unwritable manifest directories (Unix-only); full worker event sequences (progress, activities, summarising passes, request sizes, live green recoloring on `Documented`); cancellation mid-run (with and without concurrent failures); refresh-specific behavior (counting only stale directories, keeping skipped grants); scope/sigil boundary refusals for both keys and both directions (including the "boundary below the selected row" un-pact case argued via `docs/warlock-decision-un-pacting-across-a-descendant-scope.md`); in-flight refusal wording for both keys; panel/account behavior under runs interleaved with reading documents or holding conversations (asserting a run never usurps the reader's card, never leaks conversation content into the engine's requests, and never mutes the composer); reload behavior (rows update, reader's scroll/selection/collapse state preserved, failed reloads keep old tree, problems counted, message-precedence between pact and reload lines); and a nested `watching` submodule testing interaction between the file watcher and an in-flight pact/refresh (reloads deferred until the run ends, one-line "not watching" notices, precedence of messages).
