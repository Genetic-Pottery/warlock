The file implements a "pacting" system: the process of having a model pass generate a `WARLOCK.md` document for a directory, and the larger operations that run this over whole subtrees of a repository. It opens with a very long module-level doc comment explaining the whole design before any code appears, then proceeds through constants, function implementations, and finally an extensive test module that runs to the end of the file.

The doc comment lays out three layered operations. `pact_directory` handles one directory: gather its contents, describe oversized files, fit everything to a byte budget, run one model pass, and write `WARLOCK.md`, recording nothing to a manifest. `pact_subtree` runs this over a full subtree, children-first, then hashes and grants results into a manifest. `refresh_subtree` does the same subtree machinery but restricted to directories a freshness check calls stale. `pact_subtree` and `refresh_subtree` share a common core, `describe_and_grant`, which just writes documents and grants hashes over whatever directory list it's given; the difference between the two operations lies entirely in which directories are selected and what happens to entries that earn nothing.

A model request for one directory (`gather_request`) includes the directory's own files (respecting the same `ignore`-crate walk rules used elsewhere in the codebase, with `.warlock/` pruned and `.warlockignore` honored) plus each immediate child's existing `WARLOCK.md` (not deeper); editing `.warlockignore` is understood to invalidate hashes downstream as intended behavior. Two byte caps govern requests — a per-file cap and a whole-request cap — and neither can fail a pact: policy is "omit and list, never truncate." An over-cap file becomes a name+size, never truncated content. Caps are met in order: per-file first, then whole-request.

Oversized files go through a summarization pipeline: the file is chunked (UTF-8-safe, newline-respecting, bounded by a byte cap, with an oversized single line becoming its own chunk), a map pass runs per chunk, and a reduce pass combines chunk-summaries into one file summary, all through the same model-agent abstraction, producing prose describing the file's contents (never raw bytes or quotes). Both map and reduce prompts forbid naming the file, since summaries are cached by content hash independent of filename. A persistent cache lives under `.warlock/summaries/`, keyed by a versioned content hash of the file's bytes, independent of filename, path, directory, or mtime; a hit skips summarization passes entirely, misses run map-reduce and write results, cache entries are committed repo state that is never evicted, and failures reading or writing the cache can never break a pact. Summarization can decline in three ways: the file isn't text, it has too many chunks, or the passes produce nothing usable (judged only by minimum length, never phrase-list heuristics).

Fitting a whole request to its byte budget follows a "cliff becomes a ladder" design implemented as three ordered, terminating rungs: whole files become summaries (largest first, only if the summary is shorter than the original); previously-omitted files are read back and summarized if they now fit, but never restored to full bytes; and anything still carrying bytes is demoted to a bare name+size listing. A "one file, one problem entry" invariant is enforced throughout, replacing rather than duplicating problem records. Child documents from immediate children are never demoted or dropped by this ladder, even if pathologically large — regular files give way instead.

A model's answer for a directory is accepted or rejected based only on being an agent error or falling under a minimum byte threshold after trimming (no phrase-based heuristics); accepted answers are written verbatim via an atomic temp-file-plus-rename scheme mirroring how the manifest itself is saved.

The set of directories a subtree pact covers is defined by the same walk used to load a tree, listed children before parents. `pact_subtree` is explicitly two-phase: first write every document, then hash and grant every directory, because a per-directory interleaved loop would be wrong. A directory whose document failed gets no manifest entry; ancestors of a failure get an entry with no grant, which downstream freshness logic reads as stale/yellow. Hash failures during the second phase are recorded as a distinct failure type (document written, entry recorded, no grant), which is different from a hash failure encountered while `refresh_subtree` checks staleness — there it's not treated as a failure at all, just as "needs describing."

An observer mechanism lets a caller be told which directory is about to be processed (with position/total counts) and can cancel the pact between directories (never mid-pass, since the underlying agent process is out of this code's control); a separate hook announces individual summarization passes as they run; a no-op observer is provided as the default. Cancellation is not treated as failure — it just yields a smaller pact, and the second phase only grants what the first phase actually wrote.

Un-pacting a subtree is pure manifest editing: it never deletes `WARLOCK.md` files from disk, only removes manifest entries for a directory and its descendants (matched by path segment, not string prefix, so sibling directories with overlapping name prefixes are correctly distinguished).

Following the doc comment, the code itself begins with imports (standard library collections/path/fs/fmt, a directory-walking crate, and a long list of internal types and functions) and a block of heavily-commented constants: the manifest directory name, the summary cache's directory name and file extension, a versioned domain-separation string for cache keys, the output document's filename, a sentinel name for the repository root module, a walk-depth constant (directory itself, its files/children, and children's files, keeping only `WARLOCK.md` from that last level), the per-file and whole-request byte caps, a minimum document byte size, a chunk byte cap, a maximum chunk count, a minimum summary byte size, and the literal prompt texts sent to the model for directory documentation, chunk summarization ("map"), and summary combination ("reduce") — each with reasoning about wording and about why the tool uses one-shot headless invocations per directory rather than a longer session.

The functions themselves, in order, are: `pact_subtree` (computes the pactable directory set, delegates to the shared core, wraps the result); `refresh_subtree` (filters the pactable set down to stale directories via a freshness check, delegates to the same core, and merges results into the manifest without dropping anything not covered); the private `trim_to_budget` (demotes the largest whole files first, breaking ties by path, until under budget or nothing left); and the private `summarise_over_cap`, which re-reads each over-cap file's bytes, looks up or computes its summary through a `Summarising` helper bundling directory/root/agent/observer, and replaces the omitted entry with a summarized one, adjusting the problem list accordingly.

Continuing this machinery: after rebuilding the request only if something actually changed, `demote_to_budget` implements the three-rung fitting scheme described above via three helpers (`demote_whole_files`, `lift_from_the_cliff`, `list_over_budget`) plus a `report` helper enforcing the one-problem-per-file rule. The `Summarising` struct's `summary_of` method checks the cache before running passes and writes fresh results back (ignoring write failures). `chunk_utf8` performs the UTF-8-safe, newline-respecting chunking. `summarise_file` runs the map-reduce sequence over an agent, stopping at the first failure and notifying the observer before each pass. `summarising_pass` executes one call and validates/trims the result against the minimum summary length. `map_request` and `reduce_request` build the actual prompts, embedding chunk text directly rather than as an attached file, so a chunk is never confused with a whole file. The disk-backed summary cache is implemented by five small functions: `summary_key` (content-only hash), `summary_dir`, `summary_file_name`, `cached_summary` (any read failure is treated as a miss), and `cache_summary` (atomic write via temp file and rename).

Directory walking itself is done by `walk`, populating a `Found` struct (files and child documents, both kept in ordered maps for determinism), respecting the depth limit and ignore rules; `relative` renders a path in the manifest's relative forward-slash spelling. Byte accounting is handled by `byte_count`, `file_bytes` (full bytes, summary length, or zero depending on a file's state), and `carried_bytes` (total budget usage). The observer/progress system consists of the `Observer` trait (`starting`, returning continue/stop; `summarising`; `documented`, the latter two defaulting to no-ops), the `Pacting` continue/stop enum, and the trivial `Unwatched` implementation. Result and error types include `PactedSubtree`, `Pacted`, `Gathered`, `Problem` (path plus cause, with Display/Error impls), the non-exhaustive `Omission` enum (`TooLarge`, `OverBudget`, `Unreadable`, `NotText`, `TooManyChunks`, `Unsummarised` with an optional underlying error), `Refusal` (why a directory-level pass produced no document: an agent error or a too-short answer), the non-exhaustive `Error` enum (`Walk`, `Path`, `Refused`, `Write`, each naming a directory, with a `directory()` accessor), and the non-exhaustive `Failure` enum (`Document`, `Record`, `Hash`, similarly directory-scoped).
