This file implements an asynchronous "pact" run — a background documentation-writing operation that walks a directory subtree, drives an AI agent ("claude") to write a `WARLOCK.md` file per directory, and reports progress back to a terminal UI — followed by an extensive test module covering that behavior.

The module doc comment explains the design rationale: the pact keystroke is the one action that writes to disk and takes over a frame, so it runs off the UI thread via a worker; the three key functions are `pact_press`, `spawn_pact`, and `apply_progress`. Esc-cancel lets the worker finish hashing/saving/reporting what it already completed, whereas quitting drops the cancel guard and kills the in-flight `claude` process outright, discarding nothing already recorded.

It imports from the standard library (`path`, `sync::mpsc`, `time::Instant`, `fs`, `io`, `thread`), from `warlock_engine` (`Agent`, `Manifest`, `NodeState`, `PactFailure`, `PactObserver`, `PactProblem`, `PactedSubtree`, `Pacting`, `Tree`, `pact_subtree`, `to_manifest_path`, `unpact_subtree`), from `warlock_tui` (`Activities`, `Activity`, `App`, `Cancel`, `ClaudeAgent`, `Outcome`, `PactToggle`, `Section`), and from local `error` and `session` modules.

Two footer-message constants are defined: `PACT_LOST` (shown if the worker thread died without reporting, implying a panic) and `PACT_CANCELLED` (shown when the user pressed Esc, explaining only completed work is recorded). A further constant, `DOCUMENT_FILE = "WARLOCK.md"`, names the file each pacted directory receives.

Core types:
- `Running`: held by the event loop while a pact is in progress — the event receiver, a `CancelGuard`, the subtree path being pacted, and a snapshot (`before`) of the `App` for restoration if nothing was recorded.
- `CancelGuard`: wraps a `Cancel` handle and cancels on `Drop`, guaranteeing no orphaned `claude` process however the loop exits; exposes `new`, `handle`, `cancel`, `is_cancelled`.
- `PactEvent`: enum of everything the worker can report — `Starting` (directory, position, total), `Doing(Activity)`, `Summarising` (chunked large-file progress: file, part, parts), `Documented` (a subtree fully delivered, triggering immediate green recoloring), and `Finished(Result<Toggled, String>)`, sent exactly once.
- `Toggled`: result of a toggle — updated `manifest`, `granted` bool, optional `message`, and `refusals` (`Vec<Refusal>`).
- `Refusal`: a failing directory paired with a one-line reason, with a `From<&PactFailure>` conversion.

Helper/adapter functions: `activity_port` builds an `Activities` port forwarding `Activity` events over the channel (ignoring send failure, meaning the app is quitting); `Reporting<'a>` implements `PactObserver`, wiring `starting`/`summarising`/`documented` callbacks to channel sends and checking `Cancel` at `starting` to choose `Pacting::Continue` vs `Stop`.

Thread orchestration: `spawn_pact` clones manifest/root/toggle, builds a run-specific `ClaudeAgent` with its own cancel handle and activity port, spawns a thread running `run_pact`, and returns the receiver without joining (safe because each worker owns its state and manifest writes are atomic write-then-rename). `run_pact` is the worker body, calling `apply_toggle`, rewriting a cancelled outcome via `cancelled()`, and always sending exactly one `Finished` event. `cancelled` turns a `Toggled` outcome into a cancelled one (`granted: false`, message set to `PACT_CANCELLED`, manifest left as saved).

Front-end/dispatch functions: `pact_press` decides what a keypress does — refuses (setting an "already running" flag) if a run is in flight, otherwise calls `app.toggle_pact()` and, for a pact (not un-pact), starts a new panel "account" at the given time. `apply_progress` is the main per-frame integration function: it drains buffered `PactEvent`s non-blockingly, updates app state per event (opening account sections on `Starting`, recording activities, updating summarizing status, recoloring finished subtrees green on `Documented`), and on `Finished` or channel disconnect finalizes the run — applying the new manifest and possibly full-subtree coloring, setting messages, or restoring prior state via `restore()` on failure/panic — then calls `close_account` to close panel sections and `reload_tree` to reload the tree from disk, returning the newly loaded `Tree` on success.

Supporting functions: `close_account` closes each open panel section with an appropriate `Outcome` (via `section_outcome`), marks a cancelled section specially, and finalizes the account timer. `section_outcome` determines a section's final `Outcome`, checking refusals by directory name (via `section_label`) or else statting the `WARLOCK.md` file on disk for bytes written or missing/unreadable status. `restore` rolls the `App` back to a prior snapshot while preserving account/log data and setting a message. `section_label` computes a directory's display path relative to the tree root (via `to_manifest_path`), falling back to the absolute path.

The central engine-calling function `apply_toggle` performs the actual pact/un-pact by calling `pact_subtree`/`unpact_subtree`, computing `granted`/`message`/`refusals`, and saving the manifest once at the end, returning `Result<Toggled, String>`. `pact_message` builds the one-line footer summary from lists of `PactFailure` and `PactProblem`, showing the first item's message in full and counting the rest ("(and N more)").

The remainder of the file is a `#[cfg(test)] mod tests` block (no further production code). It defines extensive scaffolding: a `ROOT` constant for a synthetic repo path; `Canned`, a fake `Agent` that returns canned markdown, can be configured to refuse specific directories, cancel at a given directory, and report activities, and records which directories were requested and whether a manifest existed at request time; and helper functions including `document()` (filler text passing length checks), `saved()` (reads manifest from disk), `Scratch` (a temp-directory-backed test repo with `write`/`path`/`Drop` cleanup), `toggle()`, `one_crate()`/`one_crate_to_load()`/`two_crates` (sample repo builders), `load()` (builds `App`+`Scope`), `at()` (instant arithmetic), `panel_text()` (renders account lines as strings), `nowhere()` (a `Scope` for a nonexistent tree), `state_of()`, `documents()`, `run_and_apply()` (runs `run_pact`+`apply_progress` together), `over_the_cap()`/`stand_in()` (oversized file content / a shell script simulating a real `claude` process stream), `recorded()` (runs `run_pact` synchronously against `Canned` to capture a real `PactEvent` sequence), `replay()` (feeds that sequence into `apply_progress` frame-by-frame at 10-second intervals, with a `FRAME = 10` constant), `document_bytes()` (reads written document size), and (in a nested `mod watching`) `unwatched()` (builds a `Watched` with `Watching::Off` over a loaded scope).

A nested `mod watching` block tests filesystem-watcher-driven reload behavior using a `Watched`/`Watching::Off`/`WatchPolicy` abstraction rather than a real OS watcher, referencing constants `QUIET_PERIOD`, `RELOAD_CEILING`, and `POLL_INTERVAL`. Its tests cover: a simulated write event only triggering `watched.round()` to reload after the quiet period elapses, with all reader UI state (including header) surviving; writes during an in-flight run not triggering reloads even past quiet/ceiling deadlines, with the run's own end-of-run reload picking up the change and clearing an "owes reload" flag, and no double-reload on a subsequent round; and a "live updates are off" footer note (via `note()`) being shown once, staying single-line, being overridden by an existing pact message rather than the reverse, and not appearing when a working watcher is present. This nested module's closing braces, and the outer test module's, end the file.
