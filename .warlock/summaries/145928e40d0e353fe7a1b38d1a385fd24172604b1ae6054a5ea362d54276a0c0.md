This is a Rust source file implementing input translation for a terminal UI application called warlock, converting keyboard and mouse events into pure, testable intent values with no direct terminal interaction. It is organized into a module-level doc comment, the production code, and a large embedded test module.

The module doc comment frames the file's two device-specific translators (`action_for` for keys, `mouse_action` for the mouse) plus a newer keyboard layer (`press_for`) that adds a quit-confirmation gate in front of them.

Production code, top to bottom:

- Imports crossterm key/mouse types, ratatui's `Size`, and several items from a `warlock_tui` crate (`Answered`, `App`, `Focus`, `Hit`, `QuitConfirm`, `answer_for`, `hit_test`).
- `Action` enum: the set of things a keystroke can ask the app to do — Quit, CancelPact, ToggleFocus, SelectPrevious/Next, SelectPageUp/Down, SelectFirst/Last, ToggleCollapsed, TogglePactedOnly, ToggleFiles, TogglePact, Refresh, ToggleMouseCapture. Each variant has a doc comment explaining its rationale (e.g. ToggleFocus swaps keyboard focus between a tree pane and a panel pane; Refresh re-describes only stale directories rather than the whole subtree; ToggleMouseCapture hands mouse control back to the terminal for text selection/copying).
- `action_for(key, in_flight) -> Option<Action>`: pure function mapping a `KeyEvent` plus a boolean "is a pact running" flag to an `Action`. Only acts on `KeyEventKind::Press` (ignoring releases/repeats). Handles Ctrl-C (via modifier check, case-insensitive) as Quit; Esc means CancelPact when a pact is in flight, otherwise Quit; `q` always quits; Tab toggles focus; arrow keys/`k`/`j` move selection; PageUp/PageDown page the selection; `g`/`G` (case-sensitive) jump to first/last; space toggles collapse; `o` toggles pacted-only filter; `f` toggles file display; `p` toggles pact; `r` refreshes; `m` toggles mouse capture; everything else is `None`. Extensive doc comments justify each binding and the press-only restriction.
- `Pressed` enum: the outcome of `press_for` — `Leave` (quit for real), `Confirm(QuitConfirm)` (the quit-confirmation dialog consumed the key), `Act(Action)` (pass through to the app, never `Action::Quit`), or `Nothing`.
- `is_ctrl_c(key)`: helper predicate factored out so Ctrl-C is recognized identically wherever it's checked.
- `press_for(key, confirm, in_flight) -> Pressed`: the gate function. Checks Ctrl-C first (always leaves immediately). Then, if the quit-confirmation dialog is open (`confirm.highlighted()` is `Some`), routes the key through `answer_for` and translates its `Answered` result into `Pressed` — this is the only path when the dialog is open, so no other app key binding fires. Otherwise falls through to `action_for`; if that yields `Action::Quit`, it either opens the confirmation (`in_flight == false`) or leaves immediately (`in_flight == true`); any other action passes through as `Pressed::Act`; `None` becomes `Pressed::Nothing`.
- `WHEEL_NOTCH: usize = 3`: how many rows/lines one scroll-wheel notch moves.
- `MouseAction` enum: SelectNextBy(usize), SelectPreviousBy(usize), ScrollPanelDown(usize), ScrollPanelUp(usize), SelectRow(usize), ToggleCollapsed, Focus(Focus). Doc comments explain there is deliberately no hover/drag/other-button variant.
- `mouse_action(mouse, size, app, confirm) -> Option<MouseAction>`: pure translator for `MouseEvent`s. Returns `None` outright if the quit confirmation is open (pointer is inert while it's up). Otherwise runs `hit_test(mouse.column, mouse.row, size)` and matches on `mouse.kind`: `ScrollDown`/`ScrollUp` delegate to the `wheel` helper with tree vs. panel actions; `Down(MouseButton::Left)` delegates to `click`; everything else (moves, drags, releases, other buttons, horizontal wheel) yields `None`.
- `wheel(hit, tree, panel) -> Option<MouseAction>`: chooses between the two given actions based on which pane the hit landed in (tree header/row/below-rows vs. panel line); footer, border, and offscreen hits yield `None`.
- `click(hit, app) -> Option<MouseAction>`: for a `TreeRow{offset}` hit, adds `app.scroll_offset()` to the offset to get an absolute row index; if that index is past the end of `app.rows()`, just focuses the tree; if it equals the currently selected row, returns `ToggleCollapsed`; otherwise returns `SelectRow(index)`. Tree header/below-rows hits just focus the tree; panel-line hits focus the panel; footer/border/offscreen yield `None`.

Test module (`#[cfg(test)] mod tests`), heavily commented, organized in three tiers:

1. Top-level tests directly exercising `action_for`: a `press(code)` helper builds a no-modifier key press; tests cover Quit on q/Esc with no pact, Esc canceling vs q/Ctrl-C quitting during a pact, that Esc is the only key whose meaning changes in-flight (looping over a list of other codes and asserting equal behavior in/out of flight), Ctrl-C recognition (with and without shift/caps-lock riding along) versus a bare `c` doing nothing, Tab toggling focus (including during a pact, and that releases/repeats of Tab do nothing, and that Tab is the only focus-toggling key among a sample of neighbors), Up/k and Down/j for selection movement, PageUp/PageDown, lower/upper `g`/`G` for first/last (with an explicit SHIFT-modifier variant), that releases/repeats of the movement keys do nothing, space for ToggleCollapsed (including release/repeat inertness and uniqueness among sampled neighbor keys), `o` for TogglePactedOnly (with the same release/repeat and uniqueness checks, including that uppercase `O` is unbound), `f` for ToggleFiles (same pattern), `p` for TogglePact (release/repeat check only), `r` for Refresh (checked in both flight states, uppercase `R` unbound, release/repeat inert, uniqueness among neighbors, in both flight states), `m` for ToggleMouseCapture (checked in both flight states, explicitly asserted to not equal any other `Action` variant, uppercase unbound, release/repeat inert, uniqueness among neighbors), and finally two catch-all tests: unmapped keys (`x`, Enter, Left) yield `None`, and releases/repeats of Down yield `None`.

2. A nested `mod gate` testing `press_for` and the quit-confirmation flow end-to-end. It imports `Answer`, `App`, `Focus`, `QuitConfirm`, `Row`, `panel_height`, `tree_height` from `warlock_tui` and `NodeState` from `warlock_engine`. Defines: a fixed `SIZE` (80×24); an `INERT` array of 15 keycodes representing every tree-bound key plus one unbound char, used to verify the confirmation dialog swallows all of them; a `Round` enum (`Stayed`/`Left`) standing in for the event loop's `return Ok(())` behavior; helper `press`/`ctrl_c` key builders; `app_on_screen()` building a 13-row tree (root + 12 alternately pacted/unpacted directories with files) sized to the fixed terminal; `app_in_use()` which takes that app and moves every stateful field off its default (toggles file/pacted-only filters, changes selection, collapses a row, opens an account/panel session and scrolls its window, changes focus to Panel, sets a status message) — used as the "before" baseline that a no-op keypress should reproduce exactly; and `round(app, confirm, key)`, a rewritten copy of the event loop's key-handling arms that maps `Pressed` values onto `App` mutations, deliberately panicking if `CancelPact`, `TogglePact`, `Refresh`, or `ToggleMouseCapture` ever reach the app (since those require live threads/escape sequences not exercised in tests) — the intent being to catch any leak through the confirmation gate.

Individual gate tests verify: the `app_in_use` fixture is genuinely off every default field (asserted explicitly field by field, with rationale that a flattened fixture would make later leak-tests vacuous); that Esc and `q` open the confirmation (lit on "No") rather than leaving, leaving the app untouched; that every `INERT` key is swallowed at both highlight positions with no app or confirm-state change; that answering "Yes" (via `y` or Enter) leaves by the same `Pressed::Leave` path as Ctrl-C; that answering "No" (via `n`, Esc, or Enter after navigating with Left/Right first) closes the dialog and leaves the app untouched; that four consecutive Esc presses (the "reflex double-Esc") leave the confirmation closed and the app untouched; that Ctrl-C leaves instantly regardless of confirmation state or in-flight status; that a pact in flight suppresses the confirmation gate entirely (Esc cancels, `q` leaves directly) versus opening it when nothing is running; that every `INERT` key behaves identically to plain `action_for` output when the gate is closed, at both flight settings; and that key releases/repeats neither open nor answer the confirmation.

3. A nested `mod pointer` testing `mouse_action` and click/scroll behavior end-to-end, mirroring the `gate` module's two-layer approach. Imports `MouseButton`, `MouseEvent`, `MouseEventKind`, `Size`, `NodeState`, and `App`/`Focus`/`QuitConfirm`/`Row`/`panel_height`/`tree_height`. Defines a fixed 80×24 `SIZE` with an ASCII-art diagram of the resulting layout (panel pane left, tree pane right, footer at bottom, with specific documented row/column constants: `IN_TREE`=65, `IN_PANEL`=10, `FIRST_TREE_ROW`=2, `FIRST_PANEL_LINE`=1, `TREE_HEADER`=1, `FOOTER`=22); a `viewport()` helper returning the tree's row capacity; event-builder helpers `wheel_down`, `wheel_up`, `left_click`, and a generic `event`; a `rows()` builder producing 25 rows (root + 24 directories each with one file, files hidden initially); `app_on_screen()` wrapping those rows in a sized `App`; an `asks(mouse, app)` helper calling `mouse_action` with the confirmation closed; and a `round(app, confirm, mouse)` helper mirroring the event loop's mouse-handling arms (dispatching each `MouseAction` variant to the corresponding `App` method).

Pointer tests verify: the fixture's viewport is 18 tree rows and 19 panel lines (guarding the ASCII diagram's accuracy); a wheel notch over the tree pane moves selection by 3 rows in either direction, including when hovering the tree header; three-row wheel movement matches three individual keypresses and clamps at both ends of the list after repeated notches; a wheel notch over the panel scrolls it by 3 lines; that the wheel drives whichever pane the pointer is over regardless of which pane currently holds keyboard focus, and does not itself change focus; that wheel notches over the footer or over pane borders (a list of specific column/row pairs) do nothing; that a left click on a tree row selects that row and moves focus to the tree even if the panel had focus; that a click's row index accounts for horizontal window scroll offset (tested after scrolling to the last row); that a second click on the currently-selected directory row toggles its collapsed state open/closed/open again; that a second click on a file row does nothing further (files have nothing to collapse); that a click in the panel only changes focus, moving neither selection nor the panel's scroll offset; that a click on the tree header only changes focus, not selection; that a click below the last drawn row (in the pane's empty space) only focuses the tree, changing nothing else; that clicks on the footer or borders do nothing; that all other mouse event kinds (moves, drags, releases, right/middle button events, horizontal wheel) are read and dropped at various hit points; and finally that the pointer is completely inert (both wheel and click, at multiple points) while the quit-confirmation dialog is open, verified by comparing the app before and after against a fixture whose selection, panel scroll, and focus were deliberately moved off defaults beforehand.
