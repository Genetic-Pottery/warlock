This is the complete text of a Rust source module that translates raw keyboard and mouse events into intent types for a terminal UI application (warlock), plus an extensive test suite covering that translation.

Structurally, it has two main production sections followed by a large `#[cfg(test)]` module:

1. **Keyboard, first layer (`Action` enum and `action_for`)**: `Action` enumerates the app-level commands a keystroke can request — Quit, CancelPact, ToggleFocus, selection movement (previous/next/page up/down/first/last), ToggleCollapsed, TogglePactedOnly, ToggleFiles, TogglePact, Refresh, OpenScope, ViewFile, EditFile, SwapCard, ToggleMouseCapture. Each variant has a substantial doc comment explaining its semantics, refusal conditions, and relationship to other actions. `action_for(key, in_flight)` is a pure function mapping a `KeyEvent` plus an "is a pact running" flag to an `Option<Action>`, filtering to press-only events, handling Ctrl-C, and binding lower-case letters (q, j/k, g/G, space, o, f, p, r, s, v, e, m), Tab/BackTab, and arrows/page keys, with Esc's meaning depending on `in_flight`.

2. **Keyboard, second layer (`Pressed` enum and `press_for`)**: `Pressed` is the outcome after the "gate" (quit confirmation, scope prompt, write prompt, composer) has had a chance to consume the key: Leave, CancelTurn, Confirm(QuitConfirm), Scope(Edited), Write(Edited), Compose(Composed), Act(Action), Nothing. Helper functions `is_ctrl_c` and `is_tab` isolate those checks. `press_for(key, confirm, prompt, write, composer, in_flight, answered)` is the central gate function, checked in strict order: Ctrl-C first (Leave or CancelTurn depending on `answered`), then the quit confirmation dialog, then the scope prompt, then the write prompt, then the composer (muted or not, with Tab excluded), and finally falls through to `action_for`, translating `Action::Quit` into either `Confirm` or `Leave` depending on `in_flight`.

3. **Mouse handling**: `WHEEL_NOTCH` constant (3), `MouseAction` enum (SelectNextBy, SelectPreviousBy, ScrollPanelDown, ScrollPanelUp, SelectRow, ToggleCollapsed, Focus), and `mouse_action(...)` which computes intent from a `MouseEvent`, terminal `Size`, the `App`, and the three window states (confirm/prompt/write), returning `None` when any window is open. It uses `hit_test` to locate the point, then dispatches wheel events via helper `wheel()` and left-button-down via helper `click()`. Only scroll and left-button-down events are handled; everything else (drags, moves, releases, other buttons, horizontal wheel) is dropped. `click()` handles row selection, toggling collapse on a re-click of the already-selected row, and focus changes for header/blank-area/panel/composer regions.

4. **Test module** (very large, the bulk of the file): Uses `ratatui::crossterm::event` types and imports from `warlock_tui`. Top-level tests directly exercise `action_for` for every binding (q/Esc quit, Esc cancels pact in flight, in-flight parity for all other keys, Ctrl-C variants, Tab/BackTab, movement keys g/G, space, o, f, p, r, s, v, e, m — each with tests for plain behavior, release/repeat events being ignored, uppercase variants doing nothing, and cross-checks that each key is exclusive to its action).

   Nested inside is a `mod gate` testing `press_for` end-to-end: it builds fixture `App`s (`app_on_screen`, `app_in_use` — deliberately moved off every default field so leaked keystrokes would be detectable), defines a `Round` enum (Stayed/Left) and a `round`/`round_under`/`round_composing`/`round_running` family of helper functions that replicate the event loop's match arms (panicking on actions that should never leak through a window), and tests: Esc/q opening the confirmation, the confirmation swallowing all tree keys, Yes/No answers, the "reflex second Esc" behavior, Ctrl-C always leaving (or cancelling a turn if `answered`), precedence ordering among Ctrl-C/confirmation/scope-prompt/composer/keys, and a nested `mod writing` covering the write-prompt window specifically (every binding going into its field, Enter submit/Esc close, Ctrl-C precedence, composer not being consulted, scope-prompt-over-write-prompt precedence, and normal key behavior once the window closes). Another nested `mod composing` tests the composer/draft field: pairs of `types(code)` / `acts(code, action)` helper-driven tests for each letter key (p, r, s, v, e, f, g, G, j, k) confirming they're literal characters while composing and normal actions otherwise, plus tests for muted fields swallowing all keys except Tab and Ctrl-C, run-in-flight not muting the composer, submit being inert (no consumer in this slice), blank submissions producing no footer message, Ctrl-C leaving without leaking a "c", and the draft surviving Esc/focus-cycling/a run starting-and-ending.

   Finally, a `mod pointer` tests `mouse_action` and a `round`/`round_under` loop-replica for mouse events: it defines a fixed 80x24 screen layout (with documented column/row map for tree/panel panes), builds a 25-row fixture tree, and tests wheel notches over tree/panel (three rows per notch, clamped at ends), wheel affecting whichever pane the pointer is over regardless of focus, notches over footer/borders doing nothing, left-clicks selecting rows and taking focus, clicks correctly accounting for scroll offset, second-click-on-a-directory toggling collapse (but not on file rows), clicks in panel/header taking focus only, clicks below the last row, clicks on footer/borders doing nothing, all other mouse event kinds (drag, move, up, right/middle button, horizontal scroll) being read and dropped, and the pointer being fully inert while the confirmation, scope prompt, or write prompt is open.

There is no other content in this part — it is the entirety of the file's text as given.
