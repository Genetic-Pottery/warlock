# warlock

The repository root of Warlock — the freshness-ledger tool this project builds — laid out as a two-crate Rust workspace plus the top-level documents that govern it: licence, formatting policy, contribution gate, the product pitch, and the `CLAUDE.md` that defines the pact/freshness/scope vocabulary this whole codebase and this document format follow. All executable code lives one level down under `crates/`, whose `WARLOCK.md` summarises its two members — `warlock-engine` (headless domain library: freshness model, manifest format, hashing, pact/refresh/un-pact operations) and `warlock-tui` (terminal front end and the sole spawner of a `claude` subprocess) — related by a dependency edge that runs one direction only: TUI → engine, never back.

## What is here

- **`README.md`** (18.7KB) — the pitch and the full mental model: why the interface is a tree of `WARLOCK.md` documents rather than a file tree, the pact/brief/refresh workflow, the complete key-bind tables (movement, tree filters, mutating keys, composer, quit and scope prompts, mouse), the scope/sigil boundary and which keys it gates, the `/brief`–`/write`–`/chat` composer commands and how a written brief interacts with pacting, a font troubleshooting note, and the three-command Contributing gate. It states explicitly what Warlock is not: not autonomous, not a project generator, not a way to stop knowing your own codebase, not an editor, and never a writer of a project's own `README.md`. Read this before touching `crates/`; it is the intent the code has to satisfy.
- **`CLAUDE.md`** — the project instructions, reproduced verbatim between `warlock:begin`/`warlock:end` markers. It is both spec (what Warlock's own product does: the fresh/stale/unpacted vocabulary, subtree hashing, scopes and sigils, what warlock's mutating keys refuse and why) and operating instructions for whoever — human or model — works in this repository, including the directive to read `WARLOCK.md` files before source and to say when a change crosses a scope rather than acting around it.
- **`Cargo.toml`** — the workspace manifest. Declares the two members (`crates/warlock-engine`, `crates/warlock-tui`) and centralises `[workspace.package]`, `[workspace.lints]`, and `[workspace.dependencies]` so both crates inherit one ruleset rather than declaring their own. This is where project-wide hard rules live in enforceable form: `unsafe_code = "deny"` (no `unsafe` anywhere in Warlock), `missing_docs` / `unreachable_pub` / `missing_debug_implementations` / `rust_2018_idioms` all warn, `clippy::pedantic` runs as a group (`clippy::nursery` and `clippy::cargo` deliberately left off, with reasons given inline), and `clippy::dbg_macro` warns. Every dependency in `[workspace.dependencies]` carries a comment justifying its inclusion — `serde`, `serde_json` (the untrusted, extensible `stream-json` wire format the model pass is read through), `toml` (the hand-editable `.warlock/pacts.toml` format), `ratatui` (the TUI framework, whose re-exported `crossterm` is used in place of naming crossterm directly, to make frontend/backend version skew impossible), `ignore` (gitignore-aware directory walking), `blake3` (the subtree hash a grant is compared against), `notify` (cross-platform filesystem watching), plus dev-only `serde_test` and `tempfile`. A new shared dependency added without a justifying comment is a review flag.
- **`Cargo.lock`** (53.9KB) — generated, workspace-wide; not hand-edited. Confirms the two workspace members as `warlock-engine` (depending on `blake3`, `ignore`, `serde`, `serde_test`, `tempfile`, `toml`) and `warlock-tui` (depending on `notify`, `ratatui`, `serde_json`, `tempfile`, and `warlock-engine` itself) — the lockfile is the concrete evidence of the one-directional TUI→engine dependency edge the workspace is built around.
- **`rustfmt.toml`** — deliberately close to rustfmt defaults, pinned to `edition = "2024"` and `style_edition = "2024"` (so a bare `rustfmt`, not just `cargo fmt`, parses 2024 syntax correctly) and `newline_style = "Unix"` for reproducible, platform-independent formatting; `use_field_init_shorthand = true` is the one added deviation. Nothing here is nightly-only, since the local toolchain is Rust from nixpkgs stable with no rustup shims.
- **`LICENSE`** — Apache-2.0, standard text.

## What a reader has to know before changing anything

- **There is no code at this level.** Anything behavioural belongs under `crates/`; changes made directly here are workspace wiring, licensing, or top-level policy only.
- **The three checks in `README.md`'s Contributing section are the whole gate**, and run locally exactly as they run in CI: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
- **Lint changes belong in this `Cargo.toml`, not in a crate.** If a lint fires and feels wrong, the workspace-level lint table is the first place to look; any new `allow` anywhere in the tree must carry a comment saying why, per the convention already established in `[workspace.lints]`.
- **A new shared dependency goes in `[workspace.dependencies]` with a justifying comment**, following the pattern every existing entry sets.
- **This project treats its own `README.md` as sacred.** Per the "not a squatter" promise `README.md` makes about the tool it describes, Warlock the product never writes to a project's `README.md`; extend the same care editing this one by hand, since it is authored prose rather than a generated artifact — a different kind of change from editing a `WARLOCK.md`.
- **Consult `crates/WARLOCK.md`** before making any change that is not purely workspace-level wiring. It summarises `warlock-engine` and `warlock-tui` and states the one-directional TUI→engine dependency edge as the load-bearing architectural fact of this workspace, along with the note (from both member crates' own documents) that scope/sigil vocabulary is defined and partly wired — the TUI can write a scope into the manifest — but that neither crate's document describes anything that checks a held sigil against a directory's scope and blocks or warns on a mismatch.
- **`p` (whole subtree, and its own inverse) and `r` (only the already-stale members of one already-pacted subtree) are different operations, per `crates/WARLOCK.md`** — check which one a given change actually needs. Editing any `WARLOCK.md` by hand makes its own directory stale again immediately, since the document's own bytes are part of the digest recorded at the moment it was last granted.
