# warlock

The repository root of Warlock — the freshness-ledger tool this codebase builds. It holds the workspace-level configuration (`Cargo.toml`, `Cargo.lock`, `rustfmt.toml`), the project's licence, the pitch and complete reference (`README.md`), the pact/freshness/scope vocabulary the whole repository operates under (`CLAUDE.md`), and a short vocabulary crib (`CONTEXT.md`). All executable code lives one level down under `crates/`, whose `WARLOCK.md` describes its two members — `warlock-engine` (headless domain library) and `warlock-tui` (terminal front end and sole spawner of a `claude` subprocess) — joined by a dependency edge that runs one direction only: TUI → engine, never back.

## What is here

- **`README.md`** (26.9KB) — the pitch and the full mental model: why the interface is a tree of `WARLOCK.md` documents, the pact/brief/refresh workflow, the complete key-bind tables (movement, tree filters, mutating keys, composer, quit and scope prompts, mouse), the scope/sigil boundary and exactly which keys it gates, the `/brief`–`/write`–`/chat` composer commands and how a written brief interacts with pacting, the full headless CLI (`init`, `config`, `stale`, `fresh`, `check`, `unpact`, `scope add`/`remove`, `pact`, `refresh`) with its exit-status table, a font-rendering troubleshooting note, and the three-command Contributing gate. It states plainly what Warlock is not: not autonomous, not a project generator, not a way to stop knowing your own codebase, not an editor, and never a writer of a project's own `README.md`. Read this before touching `crates/`.
- **`CLAUDE.md`** — the project instructions, reproduced between `warlock:begin`/`warlock:end` markers (this is what `warlock init` writes into a project's own `CLAUDE.md`). It doubles as spec — the fresh/stale/unpacted vocabulary, subtree hashing, scopes and sigils, what warlock's mutating keys refuse and why — and as operating instructions for whoever works in this repository, including the directive to read `WARLOCK.md` files before source and to name rather than silently work around a crossed scope.
- **`CONTEXT.md`** — a short, separate vocabulary note (Pact, Fresh, Stale, Scope, Sigil, `/brief`, `/write`) that states plainly that the scope/sigil system is a guardrail rather than a hard gate — easily sidestepped, with the final human gate always a reviewed PR. It is a companion gloss, not a competing spec: it agrees with `CLAUDE.md`'s account of scopes and sigils and adds the human-review framing that `CLAUDE.md` and `README.md` do not spell out as explicitly.
- **`Cargo.toml`** — the workspace manifest. Declares the two members (`crates/warlock-engine`, `crates/warlock-tui`) and centralises `[workspace.package]`, `[workspace.lints]`, and `[workspace.dependencies]`. Hard rules enforced here: `unsafe_code = "deny"`, `missing_docs`/`unreachable_pub`/`missing_debug_implementations`/`rust_2018_idioms` all warn, `clippy::pedantic` runs as a group (`clippy::nursery` and `clippy::cargo` deliberately left off, with reasons given inline), and `clippy::dbg_macro` warns. Every workspace dependency carries a comment justifying it: `serde`/`serde_json` (the latter with `preserve_order`, for the untrusted `stream-json` wire format a model pass is read through, and so a `--json` object's keys print in the order the subcommand wrote them rather than alphabetically), `toml` (the hand-editable `.warlock/pacts.toml`), `ratatui` (whose re-exported `crossterm` is used in place of naming crossterm directly, to make frontend/backend version skew impossible), `ignore` (gitignore-aware walking), `blake3` (the subtree hash a grant is compared against), `notify` (cross-platform filesystem watching), `clap` with `derive` (the CLI surface, including a nested `scope add`/`scope remove`), `ctrlc` (the one place `unsafe` would otherwise be needed, for signal-safe Ctrl-C handling — the reason the crate is taken at all under `unsafe_code = "deny"`), plus dev-only `serde_test` and `tempfile`. A new shared dependency added without a justifying comment is a review flag.
- **`Cargo.lock`** (53.9KB, or per its own accounting 58180 bytes) — generated, workspace-wide, not hand-edited. Confirms the two workspace members as `warlock-engine` (depending on `blake3`, `ignore`, `serde`, `serde_test`, `tempfile`, `toml`) and `warlock-tui` (depending on `clap`, `ctrlc`, `notify`, `ratatui`, `serde_json`, `tempfile`, and `warlock-engine` itself) — concrete confirmation of the one-directional TUI→engine dependency edge, and that `clap` and `ctrlc` are now real, resolved dependencies of the TUI rather than aspirational entries.
- **`rustfmt.toml`** — deliberately close to rustfmt defaults, pinned to `edition = "2024"` and `style_edition = "2024"` (so a bare `rustfmt`, not just `cargo fmt`, parses 2024 syntax correctly and formatting is reproducible across toolchain bumps) and `newline_style = "Unix"` for a platform-independent `--check`; `use_field_init_shorthand = true` is the one added stylistic deviation. Nothing here is nightly-only, consistent with a local toolchain of Rust from nixpkgs stable with no rustup shims.
- **`LICENSE`** — Apache-2.0, standard text.

## What a reader has to know before changing anything

- **There is no code at this level.** Anything behavioural belongs under `crates/`; changes made directly here are workspace wiring, licensing, or top-level policy.
- **The three checks in `README.md`'s Contributing section are the whole gate**, and run locally exactly as they run in CI: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`.
- **Lint changes belong in this `Cargo.toml`, not in a crate.** Any new `allow` anywhere in the tree must carry a comment saying why, per the pattern already set in `[workspace.lints]`.
- **A new shared dependency goes in `[workspace.dependencies]` with a justifying comment**, following the pattern every existing entry sets — the comments themselves are load-bearing documentation of why the supply-chain cost was accepted.
- **This project treats its own `README.md` as sacred.** Per the promise `README.md` makes about the tool it describes — Warlock never writes to a project's `README.md` — extend the same care editing this one by hand; it is authored prose, not a generated artifact, unlike a `WARLOCK.md`.
- **`README.md` is the exhaustive account of behaviour and CLI surface; `CLAUDE.md` and `CONTEXT.md` are the vocabulary.** Where a question is "what does this key do" or "what does this exit status mean," `README.md` has the table. Where it is "what do these words mean and why," `CLAUDE.md` is the fuller spec and `CONTEXT.md` the shorter gloss that adds the human-review framing.
- **Consult `crates/WARLOCK.md`** before making any change that is not purely workspace-level wiring. It summarises `warlock-engine` and `warlock-tui`, states the TUI→engine dependency edge as the load-bearing architectural fact of this workspace, and notes that scope/sigil enforcement is split across that edge: the engine matches a held sigil against the scope covering a directory, and the TUI refuses on the answer — in the panel behind `p`, `r` and `s`, and ahead of the headless `warlock pact`/`warlock refresh`, before a model pass is spent.
- **`p` (whole subtree, and its own inverse) and `r` (only the already-stale members of one already-pacted subtree) are different operations, per `crates/WARLOCK.md`.** Editing any `WARLOCK.md` by hand makes its own directory stale again immediately, since the document's own bytes are part of the digest recorded at the moment it was last granted.
